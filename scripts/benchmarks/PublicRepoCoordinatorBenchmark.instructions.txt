Public repository Coordinator benchmark

Scope
-----
These scripts run and analyze public-repository builds without relying on
machine-specific paths. The low-level harness is cross-platform; the system
monitor and matrix orchestrator are Windows-only:

  Run-PublicRepoCoordinatorBenchmark.ps1
    Low-level single-bootstrap harness. It creates isolated worktrees, launches
    concurrent builds, and records root PIDs plus OS process start/exit times.

  Monitor-PublicRepoCoordinatorBenchmark.ps1
    Independent monitor. It is not part of the harness polling loop. Separate
    processes write high-frequency Windows counters to system.csv, full
    PID/parent/start-time snapshots to processes.csv, and launch responsiveness
    to probes.csv. Slow snapshots/probes cannot stall strict system continuity.

  Run-PublicRepoCoordinatorMatrix.ps1
    Multi-bootstrap matrix orchestrator. It verifies tool/repository identity,
    creates balanced condition orders, gates attempts on bounded machine-idle
    checks, prevents sleep, and retries invalid conditions only as a whole block.

  Analyze-PublicRepoCoordinatorBenchmark.ps1
    Revalidates raw artifacts and produces per-repository paired analysis.

Nothing under an existing result root is replaced. Always pass a new OutputRoot.
Invalid attempts remain under that root with invalid-attempt.json; never promote
or splice an individual scenario from an invalid block.

Prerequisites
-------------
1. Use PowerShell 7 (pwsh) and git. Matrix runs additionally require Windows
   performance counters.
2. Build base and candidate bootstraps from exact commits with the same pinned
   SDK, build configuration, and source-build settings. Do not rebuild either
   bootstrap after moving its checkout to a different commit.
3. Clone Roslyn and Aspire and create normal1..normal4 and high1 detached
   worktrees beneath separate work roots. The matrix runner verifies each used
   worktree commit.
4. Do not disable Defender or other security services. Their process activity is
   captured so interference remains diagnosable.
5. Do not run matrices concurrently: they share worktrees and machine capacity.

Conditions
----------
  A-no-coordinator
    Candidate binary, Coordinator disabled.

  B-base-coordinator
    Immediate pre-change base binary with Coordinator enabled.

  C-candidate-compat
    Candidate Coordinator with reservation=0 and cap=0; all builds Normal.

  D-candidate-default-normal
    Candidate Coordinator with reservation=4 and cap=4; delayed candidate Normal.

  E-candidate-default-high
    Same binary, budget, reservation, cap, build counts, and delay as D. Only the
    delayed candidate priority is High.

The paired-priority defaults are a global node budget of 16, four Normal builds
at time zero, one delayed candidate at 15 seconds, and five total builds. The
single-build compatibility design uses NormalBuildCount=1 and
CandidateBuildCount=0. Each scenario uses a unique Coordinator pipe and shuts
down build/compiler servers before and after. UseSharedCompilation=false. Aspire
disables Playwright browser provisioning.

The matrix order supersedes the low-level harness's fixed scenario order. Use the
balanced matrix for comparisons; its discarded warm-up block is never analyzed.

Cross-platform low-level harness
--------------------------------
Build the checkout with `.\build.cmd -v quiet` on Windows or
`./build.sh -v quiet` on Unix. The harness resolves bootstrap `dotnet.exe` on
Windows and bootstrap `dotnet` on Unix.

  pwsh ./scripts/benchmarks/Run-PublicRepoCoordinatorBenchmark.ps1 `
    -BenchmarkRoot '<repo>' `
    -BuildPath '<project-or-solution>' `
    -NormalBuildCount 1 `
    -HighBuildCount 0 `
    -Rounds 1 `
    -Scenarios no-coordinator

Plan-only validation
--------------------
PlanOnly writes run-metadata.json, matrix-plan.csv/json, and plan-validation.json
without restoring or building. A complete five-condition, ten-block Williams
design has zero position imbalance and zero first-order carryover imbalance.

  $common = @{
    BaseBootstrapRoot = '<base-bootstrap>\core'
    BaseExpectedCommit = 'a6ed776c8af17d3ba790a30e2d171a7191abae55'
    CandidateBootstrapRoot = '<candidate-bootstrap>\core'
    CandidateExpectedCommit = '8fe6721c8d5899c330b247918c46fb7359193981'
    RoslynRoot = '<repos>\roslyn'
    RoslynExpectedCommit = 'bc396b5e5d67af28d2aef6bfd4ab2fa8577eb44b'
    RoslynWorkRoot = '<worktrees>\roslyn'
    AspireRoot = '<repos>\aspire'
    AspireExpectedCommit = '110a63da8357af437a00d9efc5887ffdcbdfbb3c'
    AspireWorkRoot = '<worktrees>\aspire'
  }

  pwsh .\scripts\benchmarks\Run-PublicRepoCoordinatorMatrix.ps1 @common `
    -OutputRoot '<results>\plan-<timestamp>' `
    -Workload solution-propagated `
    -WarmupBlocks 1 `
    -PrimaryBlocks 10 `
    -PlanOnly

  pwsh .\scripts\benchmarks\Analyze-PublicRepoCoordinatorBenchmark.ps1 `
    -RunRoot '<results>\plan-<timestamp>'

A/B/C/D. A complete four-condition Williams design uses four primary blocks:

Machine gate and validity
-------------------------
Before each block attempt, the runner records bounded idle-gate samples. Defaults
require three consecutive acceptable samples and time out after five minutes.
Thresholds are configurable and are recorded; the runner never waits forever.
SetThreadExecutionState requests system-awake execution and is restored in
finally. keep-awake.json must report Restored=true.

Any of these invalidates the entire attempted block:

  * a missing/failed build, wrong build count, or non-empty stderr;
  * a missing/invalid root PID or OS process timestamp;
  * in paired-priority designs, a delayed candidate start outside the configured
    offset bounds;
  * a bootstrap, repository, or worktree commit mismatch;
  * a monitor startup/exit/error-log failure;
  * missing system/process/probe telemetry;
  * a system telemetry timestamp gap above MaxTelemetryGapSeconds (default 5),
    including a sleep/resume gap; or
  * a process-snapshot or probe gap above its independent, slower-cadence bound
    (defaults 15 seconds).

The next attempt reruns every condition in that block in the same order. Warm-up
blocks are marked and excluded from analysis. The analyzer independently repeats
the identity, count, exit, stderr, offset, telemetry, and keep-awake checks.

Metrics and analysis
--------------------
All analysis is separated by repository and paired within AnalysisBlockNumber;
Roslyn and Aspire are never pooled.

  CandidateDurationSec
    OS ExitTime minus StartTime for the delayed build.

  SingleBuildDurationSec
    OS ExitTime minus StartTime for the sole Normal build in a compatibility
    matrix.

  AverageNormalDurationSec
    Arithmetic mean of the four Normal build durations in that scenario.

  TotalWallSec
    Latest OS process exit relative to scenario start.

  PeakCommittedDeltaMB
    Peak system committed bytes minus the median of the first three samples.

  DescendantPeakWorkingSetMB / DescendantPeakProcessCount
    Peak descendants reconstructed from runs.csv root PID/start identity and
    processes.csv parent snapshots.

  ProcessorQueueP95 / ProbeP95Ms
    Nearest-rank 95th percentiles from system.csv and probes.csv. Probe stalls do
    not delay system.csv sampling.

  ExternalNoisePeak*
    Peak known Defender/search/update activity; diagnostic, not filtered out.

Predeclared comparisons are:

  D-vs-E
    Priority effect. Report candidate latency gain, average Normal-build cost,
    and total-wall cost together.

  B-vs-C
    Candidate-branch/compatibility overhead.

  C-vs-D
    Bundled default reservation/cap policy impact.

Single-build compatibility additionally reports:

  A-vs-C
    Candidate compatibility Coordinator overhead relative to the same candidate
    binary without Coordinator.

  A-vs-B
    Cross-binary pre-change reference; interpret cautiously because both binary
    and Coordinator state differ.

Effects are means of paired within-block log ratios (geometric paired effects),
never ratios of independent medians. Descriptive 95% intervals use deterministic
resampling of whole blocks. Exact two-sided sign-flip tests enumerate all signs
when there are at most 20 blocks. Clean matrices are explicitly descriptive and are not powered as the primary
priority inference.

Each build writes a binlog listed in runs.csv. Existing
CoordinatorNodeGrantReceived messages preserve the granted-node count. Binlogs
do not currently identify whether effective policy values came from auto or
manual configuration; this benchmark tooling intentionally does not expand the
production protocol.
